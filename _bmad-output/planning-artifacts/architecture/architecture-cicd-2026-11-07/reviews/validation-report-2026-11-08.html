Critical and high

The 14 critical and high findings, merged into 12 issues
I-1CRIT

A failed publish freezes the module's releases

Your call: D1
Found by A-1 adversary, crit R-2 rubric, high A-7 adversary, medAD-16 AD-17 AD-18
What breaks

If a publish fails after the draft exists, the module is left with a marked draft that every later run must complete first. Completing it re-runs the drift check against the live delivered/<Repo>, which that night's bump has already moved, so it fails every night. Even if it passed, the newer loader rejects the draft commit's older hexalith-ci.json after any minor release that adds a knob. Deleting the draft by hand republishes the same version from different content, which the spec forbids. Builds released about 40 times in the last month, so a bump follows almost every night.

Fix

Completing a draft must not re-check against the current state. The two candidate rules are compared in D1.

I-2CRIT

The App private key shares jobs with unlocked third-party code

Clear fix
Found by X-1 security, crit X-11 security, med V-11 verification, lowAD-7 AD-11
What breaks

The validate, deliver and nightly jobs hold HEXALITH_CICD_APP_PRIVATE_KEY. They also run uv run over PEP 723 dependencies whose transitive versions float: the verification run resolved new MarkupSafe and referencing releases at run time. They run jscpd from npm too. Any code in a job can read all of that job's secrets from runner memory, which is how the tj-actions compromise worked. The prize is the key itself: write access to Contents, Workflows and Actions on 19 repos, rotated only after a leak.

Fix

A job that reads the key runs only stdlib Python, git and SHA-pinned actions. Render, schema validation, tool tests and the duplicate scan run in separate jobs with no secrets, and clone the public modules anonymously. CiCd tools are locked with uv lock --script and run with --locked. Every token mint passes explicit repositories and permission-* inputs.

I-3HIGH

App tokens expire after one hour, but nightly holds one for five

Clear fix
Found by R-1 rubric, high V-1 verification, high A-13 adversary, medAD-7 AD-18
What breaks

An installation token lives for one hour and is revoked when its job ends. Nightly dispatches the releases, waits up to 5 h, then pushes the bump with the App. On any long night the polling, the outcome download and the bump push get 401, so builds-version never moves. The 5 h wait also nearly fills the 6 h job limit.

Fix

No App token is used more than 50 minutes after it is minted. nightly.yml becomes separate jobs: dispatch, wait and summary, scan, bump and delivery wait, and keepalive. Each job mints its own token, the wait re-mints on every cycle, and every job stays under 6 h.

I-4HIGH

outcome.json has no single writer, and nightly can't read ready

Clear fix
Found by A-2 adversary, high R-7 rubric, med S-8 spec reconcile, medAD-17 AD-18
What breaks

AD-17 has the reusable release write the outcome. That workflow finishes before the caller's publish job starts, so the outcome can only ever say ready. Nightly has no rule for ready outside the Deferred fallback. If it reads ready as success, a failed publish goes unreported. If it reads it as failure, nightly is red every night. A second upload from publish collides on the artifact name. When codeql fails, no job writes failed.

Fix

The last job that runs writes the outcome, once. publish writes published or failed. Otherwise a final if: always() job in the reusable release writes nothing, disabled, ready (fallback only) or failed, always with overwrite: true. Nightly fails any run whose conclusion isn't success, whatever the outcome says.

I-5HIGH

A skipped module never gets its workflow drift repaired

Clear fix
Found by A-4 adversary, high S-4 spec reconcile, medAD-6 AD-8
What breaks

Delivery applies the perimeter only to modules that pass their checks. Restore skips .github/workflows/** and leaves it to the next delivery. A module agent can cause the skip, for example by renaming an enabled hook's action directory. An org agent App's edit to that module's workflows then persists for as long as the skip lasts. CAP-8's one-hour bound fails for exactly the modules that are in trouble.

Fix

Every delivering run applies every module that has a delivered/<Repo> ref. A module that passes gets the new commit. A module that fails gets its last accepted render re-applied, using the perimeter library at that ref's builds-version. Both reviewers prefer this to weakening the spec's bound.

I-6HIGH

The draft's tag can land on a different commit from the one built

Clear fix
Found by A-3 adversary, highAD-16 AD-17
What breaks

Nothing fixes the draft's target_commitish, so it defaults to the default branch. The tag is then created at the head of main when the draft is published, which can be an hour or more after the build. The next version is computed from a tag that covers commits that never shipped. Setting the target to main would also make the story-3 spike pass for the wrong reason.

Fix

target_commitish is the full release SHA, the same value as the hexalith-release: trailer. publish and the nightly fallback check that the two agree before publishing. The spike publishes a draft whose target is a SHA behind main.

I-7HIGH

The App key is reachable from any CiCd branch

Your call: D2 · D3
Found by X-2 security, highAD-7 AD-21
What breaks

A repo secret is available to runs on every branch, and deliver.yml mints App tokens while it validates non-main pushes. Anyone with Workflows write on CiCd can push a branch whose workflow prints the key. That includes the CiCd-agent token and the claude, chatgpt-codex-connector and cursor Apps, which hold write access on all repos (checked live). AD-7's controls for those Apps are the guard, the drift check and delivery, and none of them covers CiCd or Builds, where all trust starts.

Fix

The options are compared in D2 (where the key lives) and D3 (which repos the agent Apps can reach).

I-8HIGH

The auto-bump trusts any new Builds tag

Clear fix
Found by X-3 security, high A-9 adversary, med S-5 spec reconcile, med R-20 rubric, low X-16 security, lowAD-10 AD-18 AD-19 AD-21
What breaks

Rulesets block updating and deleting v* tags, but not creating them. Builds has no tag ruleset today, and immutable releases are off. Anyone with Contents write on Builds can push v<major>.99.0 on a commit CI never ran. At 02:17 the bump adopts that tag for all 17 modules, and its publish composite then runs with every module's publish credentials. Separately, the bump pushes a builds-version that nothing validated, so one bad minor halts all delivery.

Fix

The bump accepts a tag only if its release was published by github-actions[bot], its commit is on Builds main, and it matches that night's Builds outcome. The bump also runs the global checks before it pushes. AD-21 says to set the rulesets to exactly the listed ones, creating any that are missing, and to restrict creation of v* tags and delivered/** branches. Immutable releases are turned on for Builds and every module.

I-9HIGH

Publish credentials aren't bound to the publish job

Your call: D2
Found by X-4 security, highAD-16 AD-17 AD-21
What breaks

The nuget.org policy names only the owner, the repo and release.yml, with no environment. So any run of a file named release.yml, on any branch, can mint a key, and that key can push any package the owner holds. The registry push pair is an org secret that any branch can read. The drift check lives inside the reusable workflow, so a drifted caller can simply not call it.

Fix

The options are compared in D2. Either way, nightly compares the live ci.yml and release.yml blobs with delivered/<Repo> before it dispatches, and a ci-workflow input other than ci.yml is rejected outside Builds.

I-10HIGH

Release jobs mix module code with write tokens and trusted outputs

Clear fix
Found by X-5 security, high X-10 security, medAD-16 AD-17
What breaks

Build and pack run the module's MSBuild and every package's build/*.targets. They do it in the same job that deletes drafts, which holds contents: write. Code there can push to main, create tags, edit drafts, and steer the version, sha and artifact outputs that publish trusts. The artifact is handed to publish by name, with no digest. A draft is trusted on its body trailer alone.

Fix

Every job in Builds' reusable workflows declares permissions:. Jobs that run module or third-party code get contents: read, no secrets, and persist-credentials: false. Draft creation, completion and deletion run in a job that runs only stdlib Python. publish downloads the artifact by ID, checks its digest, and checks each package's version and commit. A draft counts as marked only if github-actions[bot] authored it and its SHA is on main.

I-11HIGH

The release can restore caches that module code can poison

Clear fix
Found by X-6 security, highAD-12 AD-17
What breaks

CI on main runs module tests and hooks, and can write cache entries scoped to main. The release is a workflow_dispatch on main, so it reads that scope. setup-node and setup-uv cache by default, and the current Builds release path already caches ~/.nuget/packages. A poisoned entry would be packed into the published package.

Fix

Both release.yml files declare cache-mode: none. Builds sets package-manager-cache: false on setup-node and enable-cache: false on setup-uv, and uses no NuGet cache.

I-12HIGH

Nothing removes the Builds tests that assert workflow text, as CAP-15 requires

Clear fix
Found by S-1 spec reconcile, highAD-20
What breaks

AD-20 lets the rename repoint or delete tests that read a workflow by name, and story 2 is told to repoint them. Tools/test-self-ci.py asserts the text of ci.yml and build-release.yml, and Builds' CI runs it. Once repointed it is still "used", so it survives the final deletion. CAP-15's "no Builds test asserts workflow text" never becomes true.

Fix

AD-20: the rename change also deletes every test that asserts that workflow's text, including tests in frozen directories, and repoints any other test that reads it by name. Story 2's text follows through bmad-spec.

Decisions for you

Each lists the realistic options and one recommendation. Nothing changes until you choose.
D1

How a stuck draft gets completed

I-1

RecommendationOption A. Combine it with A-7's delivered-sha input, which nightly passes at dispatch to the run that creates the draft, and with I-10's digest check.

AComplete it from the run that created itrecommended

How
The creating run writes hexalith-release-run: <run-id> into the draft. A later run completes the draft from that run's release artifact, with no drift check, no green-CI check and no build. codeql, nightly-hook and the kill switch still gate it. Artifacts are kept 90 days. If the artifact has expired, the draft is deleted when no package of its version is on nuget.org; otherwise the run fails with a fixed message.
Pros
What ships is exactly what was gated and built. Bumps and schema changes can't break it, and no version ever mixes content from two builds.
Cons
It depends on artifact retention. The conventions gain a trailer, a fixed message and a retention rule. The completing run trusts an earlier run's artifact, so it needs I-10's digest check.

BPin the drift baseline in the draft

How
The draft records hexalith-delivered: <cicd-sha>. Completion re-checks against that commit, never the live ref.
Pros
The smallest text change. Every gate still runs again.
Cons
It still rebuilds at the old SHA with the newer loader, which rejects that commit's older hexalith-ci.json after any minor that adds a knob. The rebuild can also differ from packages that were already pushed.
D2

Environments for the App key and the publish credentials

I-7, I-9

RecommendationOption A. It reverses the earlier "No GitHub environment" call. That call was made so nuget.org would accept the interim Builds release, and A keeps that working by leaving Builds' policy on production until the rewrite.

ATwo environments, deployable from main onlyrecommended

How
A CiCd environment cicd-app holds the App key. Only the deliver, nightly and per-module-check jobs reference it, and PR and branch validation read the modules anonymously. Each module's publish job runs in hexalith-release, which holds the registry push pair. Each nuget.org policy names that environment and, where nuget.org allows it, scopes package IDs to the module's prefix. AD-7, AD-17, AD-21 and the Secrets convention change.
Pros
A workflow pushed on a branch can no longer read the key or mint a nuget.org key. Environments are available for public repos on GitHub Free. It closes the paths that fall outside the threat model.
Cons
It reverses an approved decision. There are 18 environments and nuget.org policies to change, in story 1 and at each onboarding. Builds' policy must stay on production until its release is rewritten.

BKeep repo and org secrets, and accept the exposure in writing

How
AD-7 states that any CiCd branch run and any release.yml run can reach these credentials, and that this is accepted under the careless-agent model.
Pros
No change to onboarding or to the nuget.org policies.
Cons
A prompt-injected agent App, or any CiCd-agent session, can take the org-wide key. Any branch can mint a key that pushes every Hexalith package.
D3

Which repos the org agent Apps can reach

I-7

RecommendationOption A if you don't run those Apps' agents in CiCd or Builds. Otherwise option B, together with D2 option A.

ARemove CiCd and Builds from their installationsrecommended

How
The maintainer sets claude, chatgpt-codex-connector, cursor and semgrep-app to "Only select repositories", leaving out CiCd and Builds. AD-21 lists this as a precondition, and AD-7 records it.
Pros
It removes the only writers to CiCd and Builds that no control covers.
Cons
Those Apps can no longer work in CiCd or Builds, and the setting has to be checked again whenever an installation changes.

BKeep them, and rely on D2 and I-8

How
AD-7 states that the agent Apps can push to CiCd main and Builds, and names the environments (D2) and tag acceptance (I-8) as the controls.
Pros
No change to how agents work.
Cons
An agent App can still push to CiCd main, which delivery trusts and ships to 17 modules within the hour.
D4

How the Windows prepare step gets solution

R-3, A-20

RecommendationOption A.

ACI passes itrecommended

How
The reusable ci.yml outputs solution, as the loader validated it. Rendered jobs for other operating systems pass it to prepare, which reads no JSON on Windows. The output joins the AD-10 public API.
Pros
Keeps one loader and no Python on Windows.
Cons
Adds an output to the public API. Jobs for other operating systems depend on the ci job's output.

BA PowerShell exception

How
On Windows, prepare reads only solution with ConvertFrom-Json, after the Linux job has loaded the document.
Pros
No change to the API.
Cons
It adds a second reader of hexalith-ci.json, which is exactly the divergence AD-4's one-loader rule prevents.
